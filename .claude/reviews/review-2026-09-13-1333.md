## Findings

Every HIGH below was opened and re-verified by the lead, most by executing the code rather than

### HIGH 1 — "Pad 1" means two different physical pads, and all sixteen disagree

- **Where:** `custom_components/mvave/event.py:200` against `custom_components/mvave/config_flow.py:180`
  and `strings.json` (`press_slot`)
- **Evidence:** `_attr_translation_placeholders = {"number": str(spec.number)}`, where `PadSpec.number`
  is "as printed on the device" (`devices/layout.py:26`) and `docs/HARDWARE-BLE.md:107` records
  "note 36 is PAD1, the **bottom-left** pad". The config flow, the pad grid drawing and
  `mvave.press_slot` all number in reading order, where 1 is the **top left**.
- **Why it breaks:** computed across the factory layout, the two numberings agree on **0 of 16**
  positions. Config-flow "Pad 1" is entity "Pad 13"; entity "Pad 1" is config-flow "Pad 13". The two
  are opposite corners. Someone pins a lamp to "Pad 1" and writes an automation on
  `event.<device>_pad_1` expecting the same pad; it fires for the other corner, and nothing on either
  screen warns of it.
- **Fix:** translate `spec.number` into reading order before it reaches the entity name, so "Pad 5"
  is one physical pad everywhere a person reads that phrase.
- **Reported as CRITICAL; demoted to HIGH** — the substance is fully confirmed, but the severity scale
  reserves CRITICAL for data loss, breach or outage, and this is a wrong result on a normal path.
- **Lead-verified: yes** — computed both numberings from `SMC_PAD_FACTORY_LAYOUT` and printed the
  16-row table; zero agreement.

### HIGH 2 — A lock pad calls `lock.open` on every tap: it can unlatch the door and can never lock it

- **Where:** `custom_components/mvave/engine/resolve.py:59`
- **Evidence:** `"lock": ("lock", "open"),` in `TAP_SERVICES`, with no reference to state.
- **Why it breaks:** `lock` is in `DOMAIN_ORDER`, so any lock in a room **auto-fills onto a pad with no
  configuration**. Ran it: tapping returns `lock.open` whether the lock reads `locked` or `unlocked`.
  Home Assistant registers `SERVICE_OPEN` with `[LockEntityFeature.OPEN]`, so this splits two ways —
  a lock that supports it is **unlatched by a pad press**, and a lock that does not raises into a
  task nobody awaits (`registry.py:140` uses `blocking=False`), leaving the pad blinking for six
  seconds and then going solid with nothing having happened. The README says "**Tap** toggles it".
- **Fix:** make the tap state-dependent — `lock.unlock` when `locked`, `lock.lock` otherwise — and
  reserve `open` for an explicit pin.
- **Lead-verified: yes** — executed both states; both return `lock.open`. Read HA's service
  registration to confirm the feature gate.

### HIGH 3 — A knob at something switched off overwrites a perfectly readable value with its minimum

- **Where:** `custom_components/mvave/engine/surface.py:568`
- **Evidence:** `elif not state.is_active:` … `value = prop.step`
- **Why it breaks:** `not state.is_active` is standing in for "the value cannot be read". That is true
  of a light's brightness — which is what the comment reasons about — and false for a thermostat's
  setpoint or a paused speaker's volume, both readable while off. Ran it: a `climate` in state `off`
  with `temperature: 21.0` takes one knob click and sends `set_temperature: 7.5`; a `media_player`
  in `idle` at `volume_level: 0.8` sends `volume_set: 0.062`. `set_temperature` does not switch a
  thermostat on, so the only effect is that the house setpoint is silently replaced and stays
  replaced until somebody notices.
- **Fix:** take the branch only when `prop.read(state) is None`, and otherwise fall through to
  `current + step * steps`.
- **Lead-verified: yes** — executed both cases and printed the resulting service calls.

### HIGH 4 — The guard that stops a refusal restarting a refusal can never run

- **Where:** `custom_components/mvave/runner.py:713`, defeated by `runner.py:640` and `runner.py:505`
- **Evidence:** `if outcome.reaction and self._playing is not None and self._reacting: return`, while
  both callers of `_settle` call `_cancel_animation()` first, which sets `_playing = None` and
  `_reacting = False`.
- **Why it breaks:** `_play` is reached from exactly one place, `_settle`; `_dispatch` and `drive`
  both cancel before calling it, with only synchronous code in between. So `_playing` is always
  `None` at the guard and the condition is never true. Tapping a dead pad twice inside a second
  therefore restarts the refusal, putting five blinks into about 1.1 s — which `frames.py` explicitly
  forbids ("**Do not make this faster or add a blink** … It has no margin at all"), the refusal being
  three flashes at 5.6 Hz with no headroom under the three-per-second limit. **The fix committed for
  this today (`c271fea`) is dead code**, and its test asserts only that the *engine* sets
  `reaction=True`, not that the runner honours it.
- **Fix:** compute the outcome before cancelling, and skip the cancel when the guard applies.
- **Lead-verified: yes** — traced every caller of `_play` and `_settle`; there is no path that sets
  `_playing` between the cancel and the check.

### HIGH 5 — Holding a pad starts the focus breathe on entities no knob can adjust

- **Where:** `custom_components/mvave/engine/surface.py:775` with `engine/resolve.py:98`
- **Evidence:** the hold is granted by domain — `Focus(entity_id) if domain in FOCUSABLE_DOMAINS` —
  and `_perform` sets `self.focus` with no check that the entity has an adjustable property.
- **Why it breaks:** ran it with a simple blind reporting `supported_features: 0` — no
  `SET_POSITION`, which is the common case for garage doors and basic covers. Result:
  `focus = cover.garage`, `pad breathing = True`, `knob_map() = {}`. The pad shows the device's one
  signal for "the knobs are pointed here" while no encoder can do anything, and the knob map that
  would explain it only appears after you turn one.
- **Fix:** only set focus when `primary_for(state)` is not `None`; otherwise treat the hold as inert
  and shudder, the way taps are already gated.
- **Lead-verified: yes** — executed; breathe on, knob map empty.

### HIGH 6 — Turning a knob before anything is focused does nothing at all, which is first contact

- **Where:** `custom_components/mvave/engine/surface.py:543`
- **Evidence:** `if self.page.knobs.get(event.knob) is None and self.focus is None: return NOTHING_HAPPENED`
- **Why it breaks:** `focus` resets to `None` on every navigation, so this is true the first time the
  device is ever touched and again on every fresh room. Ran it on an ordinary room page with a
  dimmable lamp on it: `calls=() animation=0 legend=False` — nothing, indistinguishable from a dead
  encoder. The knob map exists precisely to answer "which of these eight do anything", and it is
  suppressed exactly when somebody would first ask. The comment justifies the guard for the **index**,
  where nothing can be focused, and the same guard silently covers ordinary pages too.
- **Fix:** scope the suppression to index pages (`page.source.kind is SourceKind.PAGES`).
- **Lead-verified: yes** — executed on a room page with a controllable entity.

### MEDIUM

Verified by the lead where marked. Not all were re-executed; the severity scale only obliges
verification of CRITICAL and HIGH.

1. **A scene painted orange makes its own acknowledgement invisible.** `render.py:139` hard-codes the
   latch colour to `ACTION` (orange) while the new colour screen validates only purple, so orange on a
   scene is accepted. Ran it: `at rest orange → pressed orange`. This reinstates the press-with-no-
   result the latch was added this morning to abolish. **Lead-verified: yes.**
2. **`get_pages` says "action" for a pad that refuses.** `describe.py:111` still branches on
   `is_stateless` for a question `_reachable` now answers with `UNKNOWN_AT_REST`. Ran it: an
   `unavailable` script returns `refuses=True` from the surface while `get_pages` reports
   `shows='action'` — and `_press`'s own comment says `get_pages` is what answers that in words.
   **Lead-verified: yes.**
3. **Letting go of *back* truncates the curtain it just started.** `_dispatch` calls
   `_cancel_animation()` unconditionally; a `ButtonRelease` whose only engine effect is already done
   therefore exists solely to kill a 1.575 s animation a few frames in. Hits the room switcher every
   time. **Lead-verified: yes** (read both call sites).
4. **`right`, `play` and `record` are permanently dark and inert.** `buttons_for` lights a transport
   button only when `page.buttons` binds it, and nothing outside the engine's own tests ever sets
   `Page.buttons` or `Page.knobs`. The design brief states per-page buttons as live fact.
   **Lead-verified: yes.**
5. **`coordinator.arming` is never invalidated.** Set in the constructor and on success only; both
   failure paths in `_async_arm` return without clearing it. After one good connect, a reconnect whose
   arming fails leaves the previous session's note map in place — the runner logs "surface ready" and
   drives an unarmed device with stale notes and a stale `encoders_relative`. **Lead-verified: yes.**
6. **`DeviceInfo` with `None` wipes the device registry on every restart.** Entities are created
   before anything connects, and the registry writes `None` because it only skips `UNDEFINED`. Proved
   with a throwaway test against the real registry: a second `async_get_or_create` with `None` values
   returns `name=None manufacturer=None model=None`. The comment in `coordinator.py` that rationalises
   this — "the registry keeps what it was told first" — is backwards. **Lead-verified: yes.**
7. **A cancelled write leaves `_shown`/`_lit` claiming the pre-write grid**, so the next diff sends
   nothing and a pad stays dark. `CancelledError` is not caught by the `BleakError` handler, so the
   cache assignment is skipped after the write has already reached the device. *Not re-executed.*
8. **`_flush_knobs` pops the `knob` timer without cancelling it**, leaking a live timer every 0.15 s
   of a sustained turn; an orphan can also clear the key that `_on_state` reads as its "is a turn in
   flight" gate, and can survive unload. *Not re-executed.*
9. **Unload racing an in-flight connect leaks a 30-minute recurring timer** per reload, because
   `async_shutdown` cancels the battery timer before `_async_close` gets the lock, and the connect
   re-creates it afterwards. `_handle_disconnect` cannot save it, having early-returned on the
   `_client` that `_async_close` just cleared. *Not re-executed.* (Reported by two agents.)
10. **A pad press cancels neither the value bar nor the knob map**, and `_arm` restarts the bar timer
    on every press, so tapping pads keeps the bar on screen indefinitely. Both documents say a pad
    press cancels the HUD. *Not re-executed.*
11. **The idle timeout plays the full 1.575 s collapse.** `_go` returns from the `leaving` branch
    before the `animate` flag is ever read, so `animate=False` is unreachable. Both documents promise
    the idle return is quiet. *Not re-executed; matches a known note in the tests.*
12. **Four of the eight bus events carry no `trigger`** — `focus_set`, `focus_cleared`, `tagged`,
    `knob_turned` — so an automation calling `mvave.focus` cannot tell its own effect from a finger,
    which the README says is prevented. *Not re-executed.*
13. **`mvave.focus` on an unreachable entity makes its pad breathe**, which §5.2 forbids, and the
    knobs it claims are on it can do nothing. *Not re-executed.*
14. **A cover and six readout domains share green**, so in a room with a blind and a door sensor,
    colour cannot say which pad will act and which will only shudder. This is a recorded trade-off,
    but the collision with a *controllable* domain is not addressed in the note that defends it.
15. **The colour screen reports one class of mistake per submission** — the `elif` chain stops at the
    first — so reorganising two boxes at once costs an avoidable round trip.
16. **`pytest` is unpinned** in the pure job (`pip install pytest`) while `requirements-dev.txt` pins
    ruff, mypy and the HA harness — and `checks.yml:2` claims "Versions are pinned in
    requirements-dev.txt", which is false for pytest specifically.
17. **Third-party actions are branch-pinned** (`hassfest@master`, `hacs/action@main`) and **no workflow
    declares `permissions:`**. Reported HIGH; **demoted to MEDIUM** — private single-maintainer repo,
    blast radius is this repo. Note the agent's own fix is half wrong: `hacs/action` is a docker action
    whose `action.yml` hardcodes `image: docker://ghcr.io/hacs/action:main`, so pinning the ref does
    not pin what runs. `permissions: contents: read` is the effective mitigation. **Lead-verified: yes.**
18. **`release.yml` runs *after* publication**, so even the tag-versus-manifest check it performs is an
    alarm rather than a gate — if they disagree, HACS has already been told. Reported HIGH as "cannot
    gate CI"; **demoted and reframed** — the workflow's own header states its single job, so gating CI
    is a missing feature, and the mechanism for it is branch protection, a repo setting.

   change the longer anybody builds automations on the current names.

5. **MEDIUM 1, 2** — both are consequences of changes made today and both are small.

   what it is connected to.
